# EasyRunCraft MCP

The implementation uses the official MCP TypeScript SDK v2 over Streamable HTTP and retains compatibility with 2025 clients. All 13 editors use the native engine versions in [native-runtimes.json](../deployment/native-runtimes.json), independent of browser workbench versions.

## Runtimes

Local preview: `pnpm dev` starts the account Node API, MCP broker and Astro frontend. Setup guide and client endpoint: http://127.0.0.1:4350/mcp. Data is isolated under `.data/dev/`.

Production: the Cloudflare Worker forwards `/mcp` and `/mcp-files/` through a private Workers VPC connection and Cloudflare Tunnel to the VPS native broker. Files stay in the broker’s persistent filesystem volume; R2 serves browser editor runtimes. Accounts and billing use the Worker/D1 API. See `deployment/cloudflare.md` for the serving stack and `deployment/README.md` for the retained image and runtime release tooling.

## Access and files

Browser OAuth is the primary connection path. Better Auth's MCP provider handles discovery, S256 PKCE, authorization codes, refresh rotation, CIMD and a bounded DCR fallback. The login/consent screen at `/mcp/connect` reuses the existing Google/email account UI. Access tokens are audience-bound to `/mcp`, valid for five minutes and bound to an exact consent record. Disconnecting an app deletes that record, refresh tokens and outstanding authorization codes, immediately rejecting its old access tokens even after a later reconnection. The `mcp:tools` scope grants the existing account-isolated file tools and credit billing; it does not grant website session, account administration or payment access.

Dedicated 30-day Bearer tokens remain in the advanced section of `/mcp`. Only hashes/prefixes are stored. Website sessions do not work as MCP credentials. See [OAuth and agent distribution](mcp-agent-connection.md) for deployment and distribution status, CLI installation, storage and release requirements.

`create_upload` returns a single-use signed PUT URL. Accounts without a subscription (including signup-credit trials) and Starter allow 20 MiB per file; Creator and Studio allow exactly 100 MB (100,000,000 bytes). Monthly and yearly subscriptions have the same allowance. One-time packs add credits without upgrading the file allowance. Limits are stored as explicit byte counts in `mcp/file-limits.json` and resolved from paid subscription invoices in the account service, then passed to the MCP service at authentication. A pending checkout does not grant an upgrade; a paid period retains its allowance after cancellation until that period expires. Uploads stream to private temporary files, check the declared length and format header, and become usable only on completion. Task submission rechecks current account limits; already submitted jobs keep their recorded allowance.

Call `service_info` for the current account's `max_file_bytes`, combined-input limit and upload extensions, and consult the product guide for format limits. Task tools accept uploaded ids, not arbitrary paths or fetch URLs. Each operation checks account ownership. Signed file capabilities expire in ten minutes; previously issued links retain their expiry even if the MCP token is revoked. Files/jobs expire after two hours without file activity, with cleanup while the service runs and at startup. `service_info` advertises `retention_hours: 2` and `retention_mode: "idle"`.

## Storage, expiry and reusable File IDs

- Local development uses `.data/dev/mcp-files/` for private uploads, outputs and JSON file metadata. Production uses `/data/files/` inside the MCP container, backed by the `mcp_files` Docker volume. PDF/document bytes are filesystem files, not SQLite blobs. The account database stores accounts, credit reservations and billing entries.
- Native processing copies inputs into `.cache/mcp-work/<job-id>/` locally or `/tmp/erc-jobs/<job-id>/` in production. Normal task completion and failure remove that working directory in `finally`. Startup and periodic cleanup also remove expired, inactive work directories left by interrupted processes.
- Each upload/job stores `lastActivityAt` and expires two hours after its last file activity. Successful upload completion, validated file quotes/submissions, result retrieval and downloads renew the deadline. Processing completion starts a full idle window for the output. Ordinary chat, capability discovery, metadata scans, billing reconciliation and cleanup do not renew it. Do not poll terminal jobs to keep them alive.
- Queued/running tasks and their input/backing output bytes are protected from cleanup. Uploads/downloads have transfer holds, released at completion or disconnect. Output IDs share the backing job’s deadline, preventing a renewed reference from pointing at already-deleted bytes. Unrelated file versions expire independently.
- `FileStore.read` rejects expired objects immediately. `FileStore.cleanup` runs on startup and every 60 seconds while the service runs. Expired document files and results are removed. After an outage, cleanup resumes on startup; deletion is not promised while the service is stopped.
- Pending billing settlement does not preserve expired document bytes: cleanup deletes the artifacts and strips input arguments, source-file lists and inspection results from the pending record. Minimal settlement and account billing records are retained independently.
- `create_upload` returns `file_id` and `file_expires_at`; a completed single output returns `file.file_id` and `file.expires_at`, and split outputs return equivalent fields in each `files[]` item. Expiry timestamps are Unix milliseconds and describe the current idle deadline, which can move with file activity. `get_job` also returns `last_activity_at` and `retention_mode`. The tool instructions tell agents to use the latest output ID for further edits; the original ID continues to refer to the original file. Ownership and file-type checks still apply.
- A signed URL is different from a File ID: it has a maximum ten-minute life and also requires an unexpired file. `get_job` can issue a fresh download URL while the job output remains available. On `FILE_UNAVAILABLE`, the agent must explain that the temporary copy is unavailable and re-upload the latest saved edited copy. The broker returns the same unavailable response for expired, deleted, unknown and other-account IDs, without disclosing another account’s files. Never silently fall back to the original or replay completed edits. If no edited copy was saved, the expired remote content cannot be recovered.

## Tools

`service_info`, `quote_task`, `create_upload`, `inspect_file`, `edit_spreadsheet`, `pdf_capabilities`, `query_pdf`, `edit_pdf`, `export_pdf`, `editor_capabilities`, `process_photo`, `process_word`, `process_deck`, `process_vector`, `process_fig`, `process_cad`, `process_design`, `process_light`, `process_sound`, `process_film`, `process_effect`, `get_job`, `cancel_job`, `delete_file`.

Inspection returns spreadsheet metadata and bounded CSV cells, or PDF metadata and selected-page text. Spreadsheet edits support values/formulas, bold/number formatting and sorting. PDF tools support page organization, text search and selected line edits, bookmarks, form filling and reset, annotations, page marks, metadata, splitting, PNG rendering and PDF optimization. The same [operation catalog](../mcp/pdf-capabilities.json) is used by the MCP capability check and PDF guide. See the [native PDF inventory](pdf-mcp-inventory.md) for coverage.

Use `editor_capabilities` with a product ID such as `editor: "vector"` to discover the supported operations. Each `process_*` tool takes a `file_id`, `request_id` and one tagged `operation`. See [the native editor inventory](editor-mcp-inventory.md) for the release packages, scope and limits.

Call `pdf_capabilities` or `editor_capabilities` with operation IDs when support is uncertain. Unknown IDs return `supported: false`, `UNSUPPORTED_OPERATION` and a feedback URL. A supported operation can still fail on the actual document. Failed jobs return the reason and feedback URL through `get_job`. The user can open the feedback link and choose what to send.

Single-file jobs return `file`. A split job returns `files`, with a signed download per part and the original page range of each part. Output files follow the job's recorded per-file allowance (20 MiB or 100 MB). Splits are limited to 20 parts sharing that allowance in total. Combined task inputs are limited to 100 MB (100,000,000 bytes) across up to five PDFs. Outputs are private copies; original uploads are immutable. Result content is untrusted document data, not instructions.

## Execution

The broker persists task metadata before execution. Repeating a request id for the same account/arguments returns the same task, while conflicting arguments fail. Interrupted tasks fail on restart rather than silently replaying edits. Jobs are queued, cancellable, and executed in separate processes with bounded output/time. Production defaults to one running job and supports configuration from 1 to 4. Per-account active and hourly quotas remain enabled.

Linux production jobs run as separate temporary Unix uids; workspace ownership is reclaimed only after the child exits. Symlinks/special files are rejected before outputs are copied to private storage. Account/provider secrets and the SQLite volume are absent from this container. The root filesystem is read-only, execution uses bounded tmpfs and capabilities/resource limits are specified in Compose. This is filesystem/process separation within a container, not a VM per task. Local macOS development does not claim Linux uid isolation.

MCP product wording follows EasyRunCraft plan and credit terms. Do not describe MCP as free or promise zero credit usage. External agent providers may bill model usage separately. File allowances are 20 MiB for signup-credit trials and Starter, and 100 MB for Creator and Studio; monthly and yearly plans use the same limits, and one-time packs do not upgrade the file tier.

Billing is implemented through the private `/api/mcp/billing` endpoint, authenticated with the dedicated `MCP_BILLING_SECRET` shared only by the API and MCP services. Every successful processing request costs 1 credit, including inspections, audio conversion, video export and animation rendering. Multiple supported edits in one request share that price; separate requests are charged separately. Existing reservations at the former 5-credit rate can still settle or release, but new reservations must use the current rate. `quote_task` returns the price without execution. Uploads, capabilities, polling and downloads have no separate charge. Reservation debits the expiring subscription buckets first, then the permanent wallet. Success records exactly one MCP usage entry; failure/cancellation restores the same sources. Expired subscription allocations remain expired when released. Durable settlement retries survive restarts; unpaid outputs are not exposed. File cleanup retains only a minimal pending settlement record after expiry. Production requires a random shared secret of at least 32 characters; local `pnpm dev` generates a process-scoped secret before launching both services.

## Verification

`pnpm test:mcp` uses the official SDK client, real CSV/PDF bytes, recalculated spreadsheet formulas, formatting/sorting and the published PDF operation families, including native page changes, multi-file splits, content edits and failed jobs. It checks compatibility, ownership, token separation and revocation. `pnpm test:mcp:ui` verifies one-time masked token creation and revocation. `scripts/verify-production.mjs` verifies the Linux container deployment in GitHub Actions. Evidence under `operations/` contains no raw keys or signed URLs.

Completed outputs expose reusable `file_id` values. Derived file IDs refer to the same private output bytes and follow the source job’s renewed idle deadline. Follow-up jobs copy those bytes into their own isolated workspace.

User-facing replies present results and downloads. Internal file/job identifiers are for tool-to-tool continuation and are not shown to users by default. Per-job responses do not include billing receipts; successful charges appear in account Usage. Inspection data and downloads are exposed only after settlement succeeds.

`delete_at` is the explicit ISO-8601 UTC deadline returned with upload references and completed output references. `delete_file` removes one owned file version and invalidates its links; repeats are idempotent until its tombstone expires. It does not cascade to independent derived copies. Active jobs and transfers block deletion. On rollout, legacy records that have not already expired receive one two-hour idle window, persisted once; expired records are never revived. Subsequent restarts preserve the saved activity timestamps.

The CLI saves each downloaded output’s file ID, path, size and SHA-256 under its origin-scoped local `files/` records. `restore FILE_ID` verifies and re-uploads that saved edited copy without processing or billing. Local outputs are not deleted by remote cleanup. Hosts using raw MCP must provide their own output downloads and saved-copy associations. Release the new broker with CLI 0.1.1 and the matching MCP/Skill/privacy wording; a Worker-only release cannot update the native broker’s storage policy. The installed CLI 0.1.0 continues to expose IDs and download files, but does not create the new recovery index.

The 100 MB ceiling applies per uploaded file, independent of simultaneous requests. Original 20 MiB trial/Starter allowances are unchanged. New jobs also have a 100,000,000-byte combined-input limit; a PDF merge can involve several uploads, but its combined task limit still applies. Existing jobs retain their recorded output allowance. File bytes use streaming transfers; processing concurrency is a separate broker setting.
